# mcp-audit + Snyk Code — integration guide

> Snyk CLI commands verified against Snyk docs, 2026-05-17; check
> <https://docs.snyk.io> for updates.

mcp-audit and Snyk Code scan different layers of the same threat surface and
are designed to be run together, not as alternatives.

## 1. Why mcp-audit + Snyk Code are complementary

| Layer | Tool | What it finds |
|-------|------|---------------|
| **Config layer** | mcp-audit | Misconfigured MCP servers: tool poisoning, credential exposure in JSON configs, typosquatted packages, toxic cross-server flows, rug-pull description changes, transport misconfigurations |
| **Source layer** | Snyk Code | Vulnerabilities in your MCP server *source code*: injection sinks, unsafe deserialization, hardcoded secrets, insecure APIs |

Snyk Code reads `.js`, `.ts`, `.py`, and other source files. It does not parse
MCP config JSON or understand MCP protocol semantics — server names,
capability tags, tool descriptions, or cross-server attack paths. mcp-audit
reads `claude_desktop_config.json`, `.cursor/mcp.json`, `.vscode/mcp.json`,
and similar config files. It does not analyse source code.

Running both gives you defence-in-depth:

- Snyk catches a SQL injection sink in your custom MCP server's tool handler.
- mcp-audit catches that same server being misconfigured to run with a wildcard
  network binding, or that its tool description has been poisoned to override
  AI agent behaviour.

**A clean Snyk scan does not mean a clean mcp-audit scan — and vice versa.**

## 2. Generating SARIF output from mcp-audit

mcp-audit writes a [SARIF 2.1.0](https://sarifweb.azurewebsites.net/) file
with one result per finding. Every result includes:

- **Rule ID** (e.g. `POISON-001`, `CRED-003`, `SC-002`)
- **Severity** (`error` for CRITICAL/HIGH, `warning` for MEDIUM, `note` for
  LOW/INFO)
- **Location** pointing to the MCP config file
- **Message** with a remediation hint
- **OWASP MCP Top 10 mapping** (`MCP01`–`MCP10`) in the `taxonomies` block
  and per-rule `relationships`
- **Score metadata** (`mcp-audit/grade`, `mcp-audit/numericScore`) in
  `run.properties`

```bash
# Write SARIF to a file (--output-file / -o)
mcp-audit scan --format sarif -o mcp-audit.sarif

# Or use the GitHub Action (uploads automatically)
uses: adudley78/mcp-audit@v0.10.0
with:
  sarif-output: mcp-audit.sarif
  upload-sarif: 'true'
```

Verify the output is valid before uploading:

```bash
# Quick schema check — should print the $schema URL
python3 -c "import json,sys; d=json.load(open('mcp-audit.sarif')); print(d['\$schema'])"
# Expected: https://json.schemastore.org/sarif-2.1.0.json
```

## 3. Uploading both SARIF files to GitHub Code Scanning

The recommended path for most teams — and the only path that works without a
Snyk Enterprise licence — is to upload both SARIF files to GitHub Code
Scanning via `actions/upload-sarif` (part of
[`github/codeql-action`](https://github.com/github/codeql-action)).

**Why this works:** GitHub Code Scanning aggregates findings from every SARIF
upload into a single Security tab. Snyk Enterprise customers who have
connected their GitHub organisation to Snyk see these alerts automatically
via Snyk's GitHub SCM integration — no additional step needed.

```yaml
# Upload mcp-audit SARIF
- uses: github/codeql-action/upload-sarif@v4
  with:
    sarif_file: mcp-audit.sarif
    category: mcp-audit     # label in the Security tab

# Upload Snyk SARIF (generated by snyk code test --sarif-file-output=)
- uses: github/codeql-action/upload-sarif@v4
  with:
    sarif_file: snyk.sarif
    category: snyk-code     # separate label, no collision
```

The `category` field keeps the two result sets separate in the Security tab so
you can filter by tool.

### Direct Snyk CLI upload (Snyk Enterprise only)

If your organisation has a Snyk Enterprise subscription, you can also push
Snyk findings directly to the Snyk Web UI from CI:

```bash
# Runs Snyk Code SAST and pushes results to the Snyk project dashboard
snyk code test --report --project-name=my-repo
```

There is no equivalent "push external SARIF to Snyk" command in the public
Snyk CLI. mcp-audit findings reach Snyk Enterprise via the GitHub Code
Scanning path described above.

## 4. Interpreting findings in the GitHub Security tab

After both workflows complete, open **Security → Code scanning alerts** in
your repository. You will see findings from two tools:

| Indicator | Tool | Example rule |
|-----------|------|-------------|
| Rule IDs starting with `POISON-`, `CRED-`, `SC-`, `TRANSPORT-`, `TOXIC-` | mcp-audit | `CRED-003: AWS access key in env value` |
| Rule IDs starting with `javascript/` or `python/` | Snyk Code | `javascript/SqlInjection` |

**Triage order:** prioritise CRITICAL and HIGH mcp-audit findings first —
credential exposure in a live MCP config is typically a more immediate risk
than a source-code smell. Then address HIGH/MEDIUM Snyk Code findings for
injection sinks in the server's tool handlers.

**Annotations on PRs:** both tools annotate pull-request diffs. mcp-audit
annotations point to lines in JSON config files; Snyk annotations point to
lines in source files. Reviewers see both sets without leaving the PR.

**OWASP MCP Top 10 column:** mcp-audit findings carry
[OWASP MCP Top 10](https://owasp.org/www-project-mcp-top-10/) codes
(`MCP01`–`MCP10`) in the SARIF `taxonomies` block. GitHub Code Scanning does
not currently surface taxonomy tags in the UI, but they are queryable via the
[Code Scanning API](https://docs.github.com/en/rest/code-scanning) if you
need to pivot by OWASP category in a SIEM or compliance report.

## 5. Example workflow (both tools in CI)

See the complete copy-paste workflow at
[`examples/github-actions/with-snyk.yml`](../examples/github-actions/with-snyk.yml).

It runs:

1. `snyk/actions/node@master` — Snyk Code SAST on the repository source,
   saves SARIF to `snyk.sarif`.
2. `adudley78/mcp-audit@v0.10.0` — mcp-audit config scan, saves SARIF to
   `mcp-audit.sarif`.
3. Two `upload-sarif` steps — uploads both SARIF files to GitHub Code Scanning
   with separate `category` labels.

The two scan steps run in parallel (separate `needs:` paths or same job with
`continue-on-error: true` on each step) so neither blocks the other.

### Choosing a severity threshold

| Team posture | mcp-audit threshold | Snyk threshold |
|---|---|---|
| Visibility only (new adoption) | `info`, `fail-on-findings: false` | `--severity-threshold=low` |
| Standard gate | `high` (default) | `--severity-threshold=high` |
| Strict gate | `medium` | `--severity-threshold=medium` |

Both tools support the same four severity levels (critical / high / medium /
low) and both exit 1 when findings at or above the threshold are present.

## Quick reference

```bash
# mcp-audit: scan and write SARIF
mcp-audit scan --format sarif -o mcp-audit.sarif

# Snyk Code: scan source and write SARIF
snyk code test --sarif-file-output=snyk.sarif

# Snyk Code: scan and push to Snyk Web UI (Enterprise)
snyk code test --report --project-name=my-repo

# Upload both SARIF files to GitHub Code Scanning (free)
# See examples/github-actions/with-snyk.yml for the full workflow
```
